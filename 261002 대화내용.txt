네. **2026년 10월 2일 기준으로 라이선스를 다시 확인했고, 라이선스 위반 가능성을 낮추는 방향으로 다음 단계 설계까지 진행했습니다.** 법률 자문은 아니지만, 공개 저장소의 현재 LICENSE/TRADEMARK 문서를 기준으로 판단했습니다.

| 프로젝트 | 현재 라이선스 | 새 프로젝트에 활용 |
|---|---|---|
| GitHub Spec Kit | MIT | **적극 활용 가능** |

| Claude Code Spec Workflow | MIT | 활용 가능 |

| BMAD Method | MIT + 상표 제한 | 코드/개념 활용 가능, **BMAD 명칭·브랜딩 사용 금지** |
| devloop | Apache-2.0 | 활용 가능, 직접 코드 복사 시 Apache 고지 관리 필요 |
| Task Master | MIT + Commons Clause | **코드 직접 포함하지 않음** |

Spec Kit, OpenSpec, cc-sdd는 공식 LICENSE가 MIT입니다. :chatgpt-content-reference{index="0"} Agent OS 역시 MIT이고, Claude Code Spec Workflow와 RIPER-5도 MIT로 공개되어 있습니다. :chatgpt-content-reference{index="1"}

BMAD는 소프트웨어 자체는 MIT이지만 `BMad`, `BMad Method`, `BMad Core` 등의 이름과 브랜딩은 별도 상표권 대상입니다. 따라서 기능 아이디어는 이용해도 새 프로젝트 이름이나 로고에 BMAD를 사용하지 않는 방향으로 가겠습니다. :chatgpt-content-reference{index="2"}

`devloop`은 Apache-2.0입니다. 직접 코드를 가져오는 것도 가능하지만 Apache 라이선스 조건 관리가 추가되므로, **독립 리뷰라는 설계 아이디어만 새로 구현**하는 편이 깔끔합니다. :chatgpt-content-reference{index="3"}

가장 조심할 프로젝트는 Task Master입니다. LICENSE에 Commons Clause가 추가되어 있고 저장소 자체나 그 기능을 실질적으로 기반으로 한 경쟁 서비스 판매 등에 제한이 명시되어 있습니다. 그래서 **Task Master 소스는 복사하거나 dependency로 묶지 않고, “작업 의존성 그래프”라는 일반적인 아이디어만 독립 구현**하겠습니다. :chatgpt-content-reference{index="4"}

# 3. 기존 프로젝트에서 가져올 핵심 개념

제가 조합한다면 이렇게 합니다.

| 출처 | 가져올 부분 | 구현 방법 |
|---|---|---|
| **Spec Kit** | Constitution, Specify, Clarify, Plan, Tasks, Analyze, Implement | 기반 엔진 |
| **OpenSpec** | 변경 단위 Spec, Delta Spec, Archive | 아이디어 + 필요 부분 MIT 활용 |
| **cc-sdd** | Steering, Brownfield 분석, 다중 Agent 지원 | 구조 참고 |
| **Agent OS** | 기존 코드에서 Standards 추출 | 독립 구현 |
| **devloop** | 작성자와 Reviewer 분리 | **독립 구현** |
| **RIPER-5** | 단계별 쓰기/실행 권한 제한 | 독립 구현 |
| **BMAD** | 역할별 Agent 분리 | 일반적인 역할 모델로 독립 구현 |
| **Task Master** | Task dependency 개념 | **코드 미사용** |
| 사용자님 설계 | 권한·예외·테스트·완료조건 | **핵심 차별화 기능** |

Spec Kit 자체도 현재 `constitution → specify → clarify → plan → tasks → analyze → implement` 형태의 흐름을 지원하고, `analyze`는 구현 전에 specification·plan·task 사이의 불일치를 검사합니다. :chatgpt-content-reference{index="6"}

OpenSpec은 여기서 한 단계 다르게 **변경사항별 `proposal/spec/design/tasks`를 유지한 뒤 구현하고 archive**하는 구조가 좋습니다. :chatgpt-content-reference{index="7"}

cc-sdd는 특히 기존 프로젝트에 대해 `validate-gap`, `validate-design`을 먼저 실행할 수 있다는 점이 사용자님의 목적과 잘 맞습니다. :chatgpt-content-reference{index="8"}

# 6. 가장 중요한 차별화 기능

단순히 Spec Kit 복제품을 만들면 의미가 없습니다.

새 프로젝트의 핵심은 **Traceability Matrix**로 하겠습니다.

예를 들어:

```text
REQ-023
지출결의

        ↓

SCR-014
지출결의 작성 화면

        ↓

DATA-008
ExpenseRequest

        ↓

PERM-011
expense:create

        ↓

TC-104
정상 작성

TC-105
필수값 누락

TC-106
권한 없음

        ↓

TASK-078
API 구현

TASK-079
UI 구현

        ↓

CODE
src/api/expense.ts
src/pages/expense.tsx
```

그러면 시스템이 자동으로 검사합니다.

```text
REQ-023

요구사항       ✓

예외           ✓
```


이 경우에는 AI가

> “완성했습니다.”

라고 말할 수 없게 합니다.

이것이 사용자님이 처음 강조했던 **“기능 목록보다 완료 조건을 관리한다”**는 원칙을 시스템화한 것입니다. :chatgpt-content-reference{index="12"}

## 최종 방향

이제 방향이 상당히 명확해졌습니다.

**Spec Kit을 직접 Fork해서 개조하기보다는 `Spec Kit Extension/Preset + 독립 Multi-Agent Workflow`로 만드는 것이 좋습니다.**

그리고 핵심 차별점은:

```text
Specification
      +
Traceability
      +
Completion Criteria
      +
Permission / Error Cases
      +
Independent Review
      +
Brownfield Recovery
```

입니다.

특히 사용자님이 처음 만든 **“아이디어 → 요구사항 → 업무흐름 → 상태 → 화면 → 데이터 → 권한 → 예외 → 테스트 → 구현”** 원칙은 그대로 이 프레임워크의 핵심 원칙으로 삼는 것이 좋습니다. :chatgpt-content-reference{index="15"}

다음 구현 단계에서는 **실제로 바로 GitHub 저장소에 넣을 수 있는 v0.1 프로젝트 골격**—`README.md`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `constitution`, 10개 `docs` 템플릿, 명령/Skill 구조, Claude Code·Codex 어댑터까지—로 만드는 단계가 가장 자연스럽습니다.

지금 단계에서는 **여기서 계속 문서 설계를 정리한 뒤, 실제 프로젝트 폴더를 만들어 Codex CLI나 Claude Code가 작업하게 하는 방식이 가장 좋습니다.**

지금 대화에서 계속 모든 파일 내용을 하나씩 만드는 것도 가능하지만, 이제부터는 `README.md`, `LICENSE`, `docs/`, `specs/`, `agents/`, `workflows/`, 어댑터 등 **실제 저장소 구조를 만들고 반복 수정해야 하는 단계**라 CLI 환경이 훨씬 적합합니다.

제가 권하는 역할 분담은 이렇습니다.

```text
ChatGPT
  ↓
프로젝트 구조 / 원칙 / 명세 설계

Claude Code 또는 Codex CLI
  ↓
파일 생성 + 구현
  ↓
다른 AI
  ↓
독립 검증 / 코드 리뷰
```

# 그래서 저는 이렇게 진행하는 것을 권합니다

**지금 이 채팅을 버리지 마세요.**

여기는 계속 **설계실**로 사용합니다.

그리고 별도로:

```text
C:\projects\ai-dev-framework
```

같은 실제 작업 폴더를 하나 만듭니다.

역할은:

```text

   ↓

Architect
Specification

Claude Code / Codex CLI
   ↓
Developer

다른 CLI
   ↓
Reviewer
Tester
```

이 구조가 가장 좋습니다.

그리고 다음 단계에서 제가 해드릴 것은 **CLI에 바로 넣을 수 있는 `BOOTSTRAP.md` 또는 `MASTER_PROMPT.md`를 만드는 것**입니다.

그 안에 지금까지 논의한 **라이선스 정책 + 폴더 구조 + 개발 원칙 + 단계별 작업 순서 + 금지사항 + 완료조건**을 전부 넣겠습니다.

