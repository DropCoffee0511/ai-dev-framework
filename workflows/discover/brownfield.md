# discover — Brownfield 절차

`MASTER_PROMPT.md` §3.2의 10개 절차를 실행하는 방법이다. 규칙의 단일 출처는 `MASTER_PROMPT.md` §3.2·§5.1이며, 이 문서와 충돌하면 본문이 우선한다. 이 문서는 규칙을 새로 정의하지 않고 §3.2의 실행 방법만 기술한다.

근거: `NEXT.md` 구현 후보 3, `docs/discovery.md` 미결 #8(Brownfield 분석 방식의 절차 정의 장소), `docs/audits/audit-002.md` Greenfield/Brownfield 적용성 시나리오 지적("인벤토리·기준선 범위 형식이 없다", "어느 범위를 기준선으로 삼을지, 어떤 표로 완료를 확인할지 없다").

## 0. 기준선 범위 판정 — 조사의 첫 행동

감사 지적의 핵심은 "ERP 전체인가, 이번 변경 대상인가"가 정해져 있지 않다는 것이다. 10개 절차를 시작하기 전에 범위를 정하고 기록한다.

- 기본 기준선은 **이번 변경이 닿는 범위**다. 사용자가 말한 개선 대상 기능과, 그 기능이 직접 의존하는 화면·API·데이터·권한·테스트.
- 범위 밖은 전체 저장소 구조 한 줄 요약만 남기고 깊게 조사하지 않는다. 범위 밖 조사는 비용이며 discover가 끝나지 않는 원인이다.
- 범위 제안(포함·제외와 이유)을 `docs/discovery.md`에 적어 사용자에게 보여준다. 사용자가 다른 범위를 말하면 그 기준으로 바꾼다 (`MASTER_PROMPT.md` §22의 기록 방식).
- 조사 중 범위 밖의 위험이 보이면 조사하지 않고 위험 목록에 한 줄 기록한다. discover에서 구현·수정을 하지 않는다 (§5.1).

## 1. 절차별 확인 대상과 기록 위치

§3.2의 10개 절차를 `docs/discovery.md`의 어디에 어떻게 기록하는가의 대응 표다.

| # | 절차(§3.2) | 확인 대상 | 기록 위치(`docs/discovery.md`) |
|---|---|---|---|
| 1 | 저장소 구조 조사 | 코드 디렉터리(`src`·`app`·`packages`·`server`·`client` 등), manifest(`package.json`·`pyproject.toml`·`pom.xml` 등), 빌드·CI 설정 | 구조 표(경로·역할·비고) |
| 2 | 실행 방법 조사 | manifest의 scripts, README 실행 절차, 컨테이너·환경 변수 설정 | 실행 방법 절(명령 원문 + 출처 파일 경로). 확인 실패는 추측으로 채우지 않고 "확인 실패"로 남긴다 |
| 3 | 현재 기능 목록 추출 | 라우트·URL 선언, 메뉴 정의, API 엔드포인트, 사용자가 말한 기능 | 기능 인벤토리 표(아래 §2) |
| 4 | 주요 사용자 흐름 추출 | 화면 간 이동, 입력→승인 같은 연쇄 동작 | 흐름 목록(시작→끝, 거치는 화면) |
| 5 | API/DB/권한/상태 모델 추출 | API 선언부, DB schema·migration, 역할·권한 정의, 상태 값(enum·상수) | 각각 한 절. 권한은 UI 숨김만인지 서버 검사 위치까지 확인한다 (§9 대조의 준비) |
| 6 | 테스트 현황 조사 | 테스트 러너 설정, 테스트 디렉터리, 실제 실행 결과 1회 | 테스트 절(러너·실행 명령·통과/실패 수). 실행은 읽기 전용 명령만 |
| 7 | 문서와 구현의 불일치 조사 | 기존 문서의 주장 대 1–6의 결과 | 불일치 목록(§5.11의 분류로 태그. 이 단계에서 고치지 않는다) |
| 8 | 위험 영역 식별 | 1–7의 반복 실패·미문서화·권한 공백, §10의 주의 데이터 해당 영역 | 위험·불확실성 목록(식별자·심각도) |
| 9 | `docs/`·`specs/` 초안 생성 | 1–8의 결과 | `docs/01~10` 템플릿을 **현재 구현 기준**으로 채운다. REQ·AC는 convention §1대로 `docs/02_requirements.md`에 등록한 뒤 사용한다. 기존 동작은 관찰된 사실로 적고 선호를 섞지 않는다 |
| 10 | 개선 요구사항 분리 | 7·8에서 나온 개선 후보 | 별도 Change Spec(`specs/<change-id>/spec.md`) 초안. discover 산출물에 섞지 않는다 |

## 2. 기능 인벤토리 표 (§3.2 3번의 형식)

| 기능 | 근거(파일:위치) | 화면/API | 데이터 | 권한 | 테스트 | 비고 |
|---|---|---|---|---|---|---|

- 기준선 범위 안의 기능만 행으로 만든다. 근거를 찾지 못한 기능은 "근거 없음"으로 표시한다 — 지어내지 않는다.
- 이 표가 9번(초안 생성)의 REQ 추출 원천이다. 한 행이 최소 1개 REQ 후보다.

## 3. 완료 확인 표 — `DISCOVERY_COMPLETE` 판정 전 채움

감사 지적("어떤 표로 완료를 확인할지 없다")에 대한 답이다. 아래 칸이 전부 채워져야 Gate 근거가 된다 (convention §5.1 — 근거는 커밋된 상태).

| 절차 | 산출물 위치 | 채움 여부 |
|---|---|---|
| 0 기준선 범위 | discovery.md 범위 절 | |
| 1–8 조사 | discovery.md 각 절 | |
| 9 초안 생성 | `docs/` 해당 문서 | |
| 10 Change Spec | `specs/<change-id>/` | |

Gate 줄의 기록 위치·판정자는 convention §5.1·§5.2를 따른다 (조사를 수행한 컨텍스트가 판정자).

## 4. Brownfield 특유의 금지

- 기존 동작을 "문서가 없다"는 이유로 제거·재해석하지 않는다 (§3.2).
- 발견한 dependency를 이 단계에서 교체·추가하지 않는다. 라이선스 확인과 `THIRD_PARTY_NOTICES.md` 기록 준비까지만 한다 (§15.3).
- 기준선 밖의 대규모 재구성 제안을 이 단계에서 실행하지 않는다 (§21).
